## タスク概要

broker が受信した working イベントの activity を、DB（`update_session_activity`）と Registry（`handle_event` 経由）の双方に反映する。`sync_to_db()` の `Working` 分岐で、activity が `Some` のとき既存の `update_session_state("working")` に加えて `update_session_activity` を呼ぶ。Registry への反映は [TASK-0002](TASK-0002.md) で実装済みの `handle_event(Working{..activity})` 経路をそのまま使う。SessionUpdate 送信ロジックは不変（UI は Registry をライブ参照するため payload 拡張は不要）。

## 実装詳細

### 1. sync_to_db の Working 分岐で DB 永続 🔵

**信頼性レベル**: 🔵 *既存 `src/broker.rs:139,149-150`（Working 分岐）+ dataflow.md 機能1*

**実装ファイル**: `src/broker.rs`

`HookEvent::Working { session_id, activity }` のパターンに更新し、既存の state 更新に加えて activity が `Some` のときのみ DB へ書き込む。

```rust
HookEvent::Working { session_id, activity } => {
    let _ = db::update_session_state(&conn, session_id, "working"); // 既存・維持
    if let Some(a) = activity {
        let _ = db::update_session_activity(&conn, session_id, a); // 追加: REQ-102
    }
}
```

### 2. Registry への activity 反映 🔵

**信頼性レベル**: 🔵 *TASK-0002 実装済みの `handle_event(Working)` 経路 / dataflow.md*

**実装ファイル**: `src/broker.rs`（既存 `handle_event` 呼び出し経路）

broker は受信イベントを `handle_event` に渡すため、[TASK-0002](TASK-0002.md) で実装した「working 時に `Session.activity` を Some で更新」がそのまま機能する。broker 側に追加ロジックは不要（経路の担保のみ）。

### 3. SessionUpdate 送信は不変 🔵

**信頼性レベル**: 🔵 *architecture.md 主要設計判断（UI は Registry ライブ参照）*

UI はインメモリ Registry をライブ参照するため、`AppEvent::SessionUpdate` payload に activity を載せる必要はない。既存の SessionUpdate 送信ロジックは一切変更しない。

## 単体テスト要件

テスト配置: `src/broker.rs` の `#[cfg(test)] mod tests`（`cargo test`）

- **Working パターン更新の追従** 🔵: Given activity 付き `HookEvent::Working` / When `sync_to_db` を `:memory:` DB に対し実行 / Then DB の `activity` 列が設定され、かつ既存の state 更新（"working"）も維持される
- **activity なし working の後方互換** 🔵: Given `activity: None` の Working / When sync_to_db / Then `update_session_activity` は呼ばれず（DB activity は NULL のまま）、state は "working" に更新される

## 統合テスト要件

**broker round-trip** 🔵: broker に activity 付き working イベント（1行 JSON `{"event":"working","session_id":"sid","activity":"Edit: a.rs"}`）を Unix socket 経由で送信し、

- Registry: `registry.get("sid").activity == Some("Edit: a.rs")`
- DB: `SELECT activity FROM sessions WHERE session_id='sid'` が `"Edit: a.rs"` を返す

の双方が一致することを検証する。既存の register / state / refresh の round-trip テストが壊れないことも併せて確認する。
**信頼性**: 🔵 *REQ-101 / REQ-102 / dataflow.md プロトコル節*

## 注意事項

- 既存の Unix socket「1接続1行 JSON」構造・接続ごとの `tokio::spawn`・タイムアウトを一切変更しない。
- `update_session_state("working")` の呼び出しは残す（activity 追加は state 更新の置き換えではなく追加）。
- `activity: None` のとき DB を上書きしない（直前の activity を消さない、REQ-103 と整合）。
- DB 書き込み失敗は既存どおり `let _ =` で握りつぶし、broker の配信を止めない。
