## タスク概要

Phase 1・Phase 2 で実装した activity 取得・保持と2つの監視ビュー（プロジェクト別ポップアップ `m` / 全体ダッシュボード `M`）について、リアルタイム更新とエッジ整形の挙動を結合的に検証し、回帰しないようテストを追加・補強する仕上げタスク。

検証の主眼は4点。(1) ビュー表示中に `AppEvent::SessionUpdate` 受信および 100ms Tick で内容が更新されること（既存の再描画経路に乗っていること）。(2) エッジ整形（tool_input 欠落・改行/制御文字・unknown セッション・長文省略・スクロール境界）の最終確認。(3) working 後に refresh（PostToolUse）/ idle（Stop）が来ても activity が保持される一連の流れ（REQ-103）の結合確認。(4) 上記をカバーするユニット/結合テストの追加と既存テストの非回帰確認。

本タスクは新規ロジックの作り込みより、既存実装が要件どおり動作することの「テストによる固定化」が中心であり、不足が見つかれば最小修正で補う。

## 実装詳細

### 1. リアルタイム更新の経路確認（REQ-101） 🔵

**信頼性レベル**: 🔵 *REQ-101 / dataflow.md システム全体フロー（`AppEvent::SessionUpdate` → render、`F -.->|ライブ参照| H`）*

**対象**: `src/app.rs` の表示状態（`show_agent_popup` / `show_agent_dashboard`）と `src/ui/mod.rs` の描画関数（`render_agent_popup` / `render_agent_dashboard`）。

ビュー表示中に Registry が更新された場合、専用の再描画フックを増設せず、既存の `AppEvent::SessionUpdate` 受信時の再描画と 100ms Tick による定期再描画にそのまま乗ることを確認する。描画関数が毎フレーム `SessionRegistry` をライブ参照していれば（スナップショットをキャッシュしていなければ）、Registry の最新状態が次フレームに反映される。テストでは「Registry を更新 → 描画関数が新しい activity/state を含む行を生成する」ことを検証する。

### 2. エッジ整形の最終確認（EDGE-001/002/003/102/103） 🔵🟡

**信頼性レベル**: 🟡 *EDGE-001/002/102/103 はエッジ整形挙動の妥当な推測（requirements.md 凡例上 🟡）。🔵 *EDGE-003 は EDGE-003 + `session.rs` 自動登録挙動に接地、スクロール境界クランプは既存ポップアップ慣習に接地*

- **EDGE-001**: `format_activity()` が `tool_input` に想定キー（`command`/`file_path`/`description` 等）を持たない場合、`tool_name` のみの activity（例:「Foo」）を返し、panic/エラーにしない（🟡）。
- **EDGE-002**: `tool_input` 値に改行（`\n`）・タブ（`\t`）・制御文字を含む場合、1行へ正規化（除去または空白置換 + トリム）した activity を返す（🟡）。
- **EDGE-003**: cwd 空で自動登録された unknown/unknown セッションをダッシュボードが許容して表示する（dataflow.md 機能3 のとおり `all()` に含める）。表示・抑制いずれの方針でも、決めた挙動どおりであることをテストで固定する（🔵）。
- **EDGE-102**: 表示幅を超える activity を末尾省略記号（…）で切り詰める整形関数の境界（ちょうど幅・超過1文字）を確認する（🟡）。
- **EDGE-103 / REQ-301**: 行数が表示窓を超える場合に `j`/`k`（または scroll オフセット）で全件到達でき、先頭で `k`・末尾で `j` してもオフセットが範囲外に出ない（クランプ）ことを確認する（🟡）。

### 3. working→refresh→idle の activity 保持（REQ-103） 🔵

**信頼性レベル**: 🔵 *REQ-103 / dataflow.md「activity を含むセッション状態遷移」（Working→Done で activity 保持）*

broker のイベントハンドリングにおいて、`working`（activity=Some）受信で activity を更新後、`refresh`（PostToolUse）や `idle`（Stop）を受信しても `Session.activity` をクリアせず直前値を保持することを結合的に確認する。状態（state）は遷移するが activity は据え置きであることを、Registry の状態を直接アサートして検証する。

### 4. テスト追加と非回帰確認 🔵

**信頼性レベル**: 🔵 *REQ-404（プロジェクト規約: テスト整備）/ 既存 `#[cfg(test)]` インラインテスト方針*

上記1〜3をカバーするユニット/結合テストを、各実装ファイルの `#[cfg(test)] mod tests` に追加する。追加後 `cargo test` を全件実行し、新規ケースのグリーンと既存ケースの非回帰を出力（failures 件数）で確認する。

## 単体テスト要件

テスト配置: 各対象ファイルの `#[cfg(test)] mod tests`（`cargo test` でインライン実行）。

- **ケースa: EDGE-001（キー欠落）** 🟡
  - **Given**: `tool_name="Foo"`, `tool_input={}`
  - **When**: `format_activity("Foo", &input)` を呼ぶ
  - **Then**: `"Foo"` を返し、panic しない
- **ケースb: EDGE-002（改行/制御文字）** 🟡
  - **Given**: `tool_input.command = "a\nb\tc"`
  - **When**: `format_activity` を呼ぶ
  - **Then**: 改行・タブが除去/置換され1行（例 `"Bash: a b c"` または `"Bash: abc"`）になる
- **ケースc: EDGE-102（長文省略）** 🟡
  - **Given**: 表示幅 N と、N を超える長さの activity
  - **When**: 省略整形関数を呼ぶ
  - **Then**: 文字列長が N 以内かつ末尾が `…`、ちょうど幅のときは省略しない
- **ケースd: EDGE-103 / REQ-301（スクロール境界）** 🟡
  - **Given**: 表示窓行数より多いセッション群と scroll オフセット
  - **When**: 先頭で `k` / 末尾で `j` を行う
  - **Then**: オフセットが 0 未満・最大超過にならずクランプされ、全件が窓に到達できる
- **ケースe: EDGE-003（unknown 表示）** 🔵
  - **Given**: project/worktree が "unknown" のセッションを含む Registry
  - **When**: ダッシュボード行生成（`all()` ベース）を呼ぶ
  - **Then**: 決めた方針どおり unknown 行が表示（または抑制）される

## 統合テスト要件

`cargo test`（インライン結合テスト）で以下を end-to-end 寄りに検証する。

- **結合1: broker→registry の activity 反映（REQ-101 / REQ-102 経路）** 🔵
  - **Given**: 稼働中 Registry（`:memory:` DB 相当）
  - **When**: `working`（activity=Some "Bash: bun test"）を broker のハンドラに通す
  - **Then**: 該当 `Session.activity` が `Some("Bash: bun test")` になり、（TASK-0004 経路で）DB の activity 列とも一致する
- **結合2: working→idle 後の activity 保持（REQ-103）** 🔵
  - **Given**: 結合1 で working を反映済みのセッション
  - **When**: `refresh` → `idle` を順に通す
  - **Then**: state は遷移するが `Session.activity` は直前の `Some("Bash: bun test")` を保持し続ける

## UI/UX要件

- 表示中のビューは SessionUpdate / 100ms Tick で内容が更新され、ユーザー操作なしに最新の activity/state が見える（REQ-101）。
- 長文 activity は末尾 `…` で省略し行崩れを起こさない（EDGE-102 / NFR-202）。
- 行数超過時は `j`/`k` で全件を閲覧でき、境界でクランプされる（EDGE-103 / REQ-301）。

## 実装手順（TDD）

1. **tdd-requirements**: REQ-101/103・EDGE-001/002/003/102/103 と既存実装の差分を確認し、テストで固定すべき挙動を列挙する。
2. **tdd-testcases**: 上記ケースa〜e・結合1〜2 を洗い出す。
3. **tdd-red**: 不足挙動があれば失敗するテストとして先に記述（既に満たしていれば、回帰固定テストとして記述し現状グリーンを確認）。
4. **tdd-green**: 不足分のみ最小修正で実装し、追加テストをグリーン化する。
5. **tdd-refactor**: 整形/スクロール関数の命名・重複を整理（既存スタイルに統一、日本語コメント付与）。
6. **tdd-verify-complete**: `cargo test` と `cargo build` を実行し、**出力の failures 件数（0）と exit code（0）**で完了を検証する。

## 注意事項

- 「通るはず」「動くはず」で完了としない。**今回のメッセージ内で `cargo test` を実行し、実出力（件数・exit code）を読んでから**完了を主張すること（verification ルール）。
- REQ-101 のために新しい再描画経路を作らない（YAGNI）。既存 `AppEvent::SessionUpdate` + 100ms Tick の再描画にライブ参照で乗る設計を維持する。
- activity の保持/更新タイミングは「working 受信時のみ更新、それ以外は保持」（dataflow.md 状態遷移）。この不変条件をテストで崩さない。
- EDGE-003 は「表示 or 抑制」のどちらでもよいが、設計（dataflow.md は表示）に合わせ、決めた方針をテストで明文化する。
- 既存テストの非回帰を必ず確認する（追加だけして既存を壊さない）。
