      フリーズしないことを目視確認する
      → 実インタラクティブ確認は行わず、代わりに `resolve_claude_term_key` の複合シフト
      （tab_index詰め + worktree_idシフトの同時発生）を厳密に再現する単体テスト

      （他セッションが多数アクティブ）を汚さずに行う安全な手段がなかったため見送った
- [x] EDGE-002（プロジェクト削除確定の直後に別プロジェクトのworktree削除を確定する）を
      手動シナリオ確認し、パニックや不整合が発生しないことを確認する
      → `handle_remove_project_confirm_key`/`handle_archive_confirm_key` を読み、
      インメモリの reindex（`reindex_project_maps`/`reindex_worktree_maps`）がキー入力
      ハンドラ内で同期的に完了し、`git worktree` の実削除のみが`tokio::task::spawn_blocking`
      で非同期化されていることをコードレベルで確認。TUIのキーイベントは単一スレッドの
      メインループで直列処理されるため、2つの削除確定が競合してreindexを同時実行する余地は
      ない
- [x] 本会話の発端となった再現手順（siki プロジェクト内で `指揮者` を削除し `toronto` の
      タブが継続して更新されること）を可能な範囲で再現確認する
      → 実際の `siki` プロジェクト・`toronto` worktreeは本セッション自身を含む複数の
      アクティブセッションが共有する実環境のため、破壊的な削除操作を安全に再現することは
      できなかった。ロジックレベルでは `resolve_claude_term_key`/`resolve_terminal_key`/
      `resolve_session_key` がworktree削除後もterminal_id/session_id一致で実体を再特定する
      実装になっており、上記の複合シフトテストで同型のケースをカバー済み
- [x] `cargo clippy` に新規warningが増えていないことを確認する（既存の設定に従う）
      → ブランチ分岐元（`b10509d`）とHEADで`cargo clippy --all-targets`のユニーク警告数を
      比較（140件→138件）。新設した`resolve_terminal_key`/`resolve_claude_term_key`/
      `resolve_session_key`の`collapsible_if`警告3件はlet-chain化して解消し、全体として
      新規増加はない
