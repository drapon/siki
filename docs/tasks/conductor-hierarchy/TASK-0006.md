## タスク概要

親worktreeが削除（アーカイブ）された際、当該worktreeを `parent` として持つすべての子worktreeの `parent` を `None` に更新し、独立worktreeとして扱われるようにする（REQ-016）。

design-interview.mdはこのフックの正確な挿入位置を「`reindex_worktree_maps` 付近、`main.rs:4591-4640`と推定」と記載していたが確定できておらず、これは要件定義書の残課題（EDGE-002含む）として明示的に残されていた。**本タスクの最初の実装ステップとして、正確な削除処理の関数・行番号を現在のソースを読んで確認する調査を行う**（ユーザー決定により、別のスパイクタスクにせず本実装タスク内で行う）。

### 0. 調査ステップ: worktree削除処理の正確な位置の確認 🟡→（実装時に🔵化する）

**信頼性**: 🟡 *design-interview.md残課題より。本タスク作成時点で実地確認した暫定結果を以下に記載するが、実装着手時に必ず再確認すること*

design-interview.mdの推定（`reindex_worktree_maps`, `main.rs:4591-4640`付近）に対し、本タスクファイル作成時点での実地確認では以下が判明している（**実装時に改めて `grep`/`Read` で現在のソースを確認し、行番号のズレがないことを検証すること** — 他タスクの実装や差分マージにより行番号は変動しうる）:

- 実際の削除本体は `main.rs` 内 `fn handle_archive_confirm_key(...)`（確認時点で `main.rs:4486`付近〜）であり、`KeyCode::Char('y') | KeyCode::Enter` にマッチしたブロック内で以下を順に行っている:
  1. `siki.json` の `archive` スクリプト実行
  2. `sessions`/`terminals`/`claude_terms` からの関連エントリ削除
  3. **`config::save_worktree_display_name(&app.projects[pi].name, &wt_name, None)` の呼び出し**（project.json から worktree メタデータを削除するコメントが付いている）
  4. `app.projects[pi].worktrees.remove(wi)`（メモリからの削除）
  5. `reindex_worktree_maps(...)` 呼び出し（`sessions`/`terminals`/`claude_terms` の**インデックス再調整のみ**を行うヘルパーであり、project.jsonの削除処理はここでは行っていない）
  6. `git::WorktreeManager::remove_worktree` をバックグラウンドタスクとして実行

  **重要な確認事項** 🔴: 上記ステップ3の `save_worktree_display_name(..., None)` は、そのシグネチャ通り `meta.worktrees.remove(worktree_name)` を実行し、削除対象worktree自身の `WorktreeMeta` エントリを**まるごと削除する**（TASK-0003で判明した「Noneで削除的挙動」を持つ関数）。つまり `handle_archive_confirm_key` は既に project.json を書き換えるタイミングを1箇所持っている。**子の `parent = None` 化処理は、このステップ3の直前または直後（project.json のI/Oを増やさないよう、可能であればステップ3と同じタイミング）に挿入するのが最も自然**である。

  design-interview.mdが挙げていた `reindex_worktree_maps`（`main.rs:4591-4640`付近と推定されていた関数）は実際にはメモリ上のインデックス再構築のみを行う別関数であり、project.json 書き込みとは無関係だった。**この点で design-interview.md の推定は不正確であり、正しい挿入位置はステップ3（`save_worktree_display_name` 呼び出し箇所）である** — これが本タスクの調査によって解消される残課題の中身である。

- **実装時に必ず検証すること**: (1) 上記の関数名・行番号が実装着手時点のソースと一致するか `grep -n "fn handle_archive_confirm_key" src/main.rs` 等で再確認する、(2) TASK-0001〜0005の実装によりこの関数の内容が変化していないか確認する（本タスクはTASK-0003にのみ依存するが、実装順序次第では他タスクの変更が同じファイルに入っている可能性がある）。

### 1. 子の独立化ロジック（`src/main.rs`, `handle_archive_confirm_key` 内） 🔵

**信頼性**: 🔵 *architecture.md セクション3の該当コードをそのまま転記、REQ-016*

削除対象worktree名（`wt_name`、`handle_archive_confirm_key` 内で既にローカル変数として存在する）を親に持つ全worktreeを走査し、`parent = None` に設定する。**既存の `save_worktree_display_name(..., None)` 呼び出し（削除的挙動、project.json 上から削除対象自身のエントリを消す）とは別に**、削除対象を親とする**他の**worktreeエントリに対して `config::save_worktree_parent(project_name, child_name, None)` を呼ぶ形で実装する：

```rust
// 削除対象 `wt_name` の直接の子全員を独立化する（REQ-016）
// 孫以下は元々 wt_name を parent としていないため対象外。
// 実質的に「親を1段だけ失う」形になり、子孫のさらに下の階層構造自体は保持される。
if let Some(meta) = config::load_project_meta(&project_name) {
    let children: Vec<String> = meta
        .worktrees
        .iter()
        .filter(|(_, wt_meta)| wt_meta.parent.as_deref() == Some(wt_name.as_str()))
        .map(|(name, _)| name.clone())
        .collect();
    for child_name in children {
        let _ = config::save_worktree_parent(&project_name, &child_name, None);
    }
}
```

**実行順序の注意** 🟡: この処理は、削除対象自身の `WorktreeMeta` エントリを消す `save_worktree_display_name(..., None)` の**前**に実行すること（`load_project_meta` で子を走査する時点ではまだ削除対象自身のエントリが存在していても問題はないが、逆に削除対象を先に消してしまうと、削除対象自身のエントリに何らかの子情報の手がかりが残っていた場合に失われる可能性があるため、安全側で「子の独立化 → 自身の削除」の順にする）。ただし `parent` の判定は子側のエントリの `parent` フィールドを見るだけであり、削除対象自身のエントリの有無には依存しないため、実際にはどちらの順序でも動作上の差異はない 🟡。

`app.projects[pi].worktrees` （メモリ上）側の各 `Worktree.parent` も、次回 `Project::from_config` 相当の再読み込みが起きるまでは古い値のままになる可能性があるため、メモリ上の `Worktree` に対しても同様に `parent = None` を設定するか、あるいは次回描画時に project.json から作り直す設計にするかを実装時に確認すること 🟡 *design資料にメモリ側の即時反映についての明記がないため、既存の `display_name` 更新パターン（`main.rs:1851`付近、`wt.display_name = display_name.clone()` のようにメモリとproject.jsonを両方更新する）に倣い、`app.projects[pi].worktrees` 内の対象子エントリの `parent` もその場で更新することを推奨する*。

### 2. 既存動作への影響（回帰安全性） 🔵

**信頼性**: 🔵 *REQ-016の記述、既存削除フローの構造より*

子を持たないworktreeを削除する場合、上記の走査で `children` が空 `Vec` になるため、ループは何もせず即座に既存の削除フロー（`save_worktree_display_name`, `worktrees.remove(wi)`, `reindex_worktree_maps`, git worktree削除）へ続く。既存動作（削除される側自身の挙動）には一切変更がない。

### 3. EDGE-002（親削除と子削除の同時競合）はスコープ外 🔴

**信頼性**: 🔴 *requirements.md EDGE-002自身が「本要件では規定せず設計フェーズで詳細化する」としており、architecture.md/dataflow.mdでも一貫して未規定のまま残されている*

親worktreeの削除処理（子の`parent=None`化を含む）と、その子worktree自体の削除が同時に発生する競合シナリオ（例: 親削除の `handle_archive_confirm_key` 実行中に、別の操作で子も同時に削除される）は、本要件・本タスクのスコープ外として扱う。TUIは単一プロセス・単一スレッドのイベントループ（`main.rs`のイベントループ）でキー入力を順次処理するため、通常の人間操作下では真の同時実行は起こりにくいと考えられるが 🟡、MCPツール経由の `move_worktree`/将来の `spawn_child_worktree` 等との競合可能性まで含めた厳密な排他制御の設計は行わない。**本タスクでの要件は「クラッシュしない（panicしない）」ことのみ**であり、具体的な整合性保証は行わない。

## 基本的な単体テスト要件

**信頼性**: 🔵 *architecture.md セクション3、REQ-016より*

### 親削除時の子独立化

- **Given**: 親worktree `A` に対し、`parent=Some("A")` を持つ子worktree `B`, `C` が存在する project.json
- **When**: `A` の削除処理（`handle_archive_confirm_key` の 'y' 確定分岐、または同等の削除ロジックを直接呼ぶユニットテスト）を実行する
- **Then**: 削除後の project.json で `B.parent == None` かつ `C.parent == None` になっている

### 子を持たないworktreeの削除（回帰安全性）

- **Given**: 誰の親でもない独立worktree `D`
- **When**: `D` を削除する
- **Then**: 他のworktreeの `parent` フィールドに一切変化がなく、既存の削除フロー（メタデータ削除・メモリ削除・reindex・git削除）が変更前と同一に動作する

### 削除後の子の独立動作

- **Given**: 上記「親削除時の子独立化」を実行した後の状態
- **When**: 子worktree `B` を通常のworktreeとして選択・操作する
- **Then**: `B` は独立worktreeとして問題なく選択・利用でき、削除された親 `A` への参照によるエラーや不整合が発生しない

### EDGE-002（クラッシュしないことのみ確認、詳細な整合性保証は対象外）

- **Given**: 親 `A` の削除処理が進行中に、子 `B` に対する何らかの操作（削除・付け替え等）が割り込むような極端なテストシナリオ（実装可能な範囲でモック化する）
- **When**: 両者がほぼ同時に発生する
- **Then**: panicやクラッシュが起きないことのみを確認する。整合性（`B` が最終的にどの状態になるか）についてはテストで固定の期待値を設けず、EDGE-002が本タスクのスコープ外であることをコメントで明記する 🔴
