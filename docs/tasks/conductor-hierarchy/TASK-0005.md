### 2. `build_entries` の親子DFS化（`src/ui/left_panel.rs`） 🔵

**信頼性**: 🔵 *architecture.md セクション7の該当コードをそのまま転記*

現状の `build_entries`（`src/ui/left_panel.rs:30-44`）は以下の通り、単純な `for` ループでフラットに詰めているだけ：

```rust
pub fn build_entries(projects: &[Project]) -> Vec<ListEntry> {
    let mut entries = Vec::new();
    for (pi, project) in projects.iter().enumerate() {
        entries.push(ListEntry::Project { index: pi });
        if !project.collapsed {
            for (wi, _wt) in project.worktrees.iter().enumerate() {
                entries.push(ListEntry::Worktree { project_index: pi, worktree_index: wi });
            }
        }
    }
    entries
}
```

これを以下の親子DFSへ書き換える（`children_of: HashMap<Option<&str>, Vec<usize>>` で親名→子worktree_indexリストを構築し、再帰 `dfs` ヘルパーで深さ優先に `entries` へ積む）：

```rust
pub fn build_entries(projects: &[Project]) -> Vec<ListEntry> {
    let mut entries = Vec::new();
    for (pi, project) in projects.iter().enumerate() {
        entries.push(ListEntry::Project { index: pi });
        if !project.collapsed {
            // parent名 -> 子のworktree_indexリスト（挿入順=既存Vec順を保持）
            let mut children_of: HashMap<Option<&str>, Vec<usize>> = HashMap::new();
            for (wi, wt) in project.worktrees.iter().enumerate() {
                children_of.entry(wt.parent.as_deref()).or_default().push(wi);
            }
            fn dfs(
                pi: usize, parent_key: Option<&str>, depth: usize,
                worktrees: &[Worktree], children_of: &HashMap<Option<&str>, Vec<usize>>,
                entries: &mut Vec<ListEntry>,
                visited: &mut std::collections::HashSet<usize>, // 🟡 防御的循環対策
            ) {
                if let Some(children) = children_of.get(&parent_key) {
                    for &wi in children {
                        if !visited.insert(wi) {
                            continue; // 循環データ破損時の無限再帰防止
                        }
                        entries.push(ListEntry::Worktree { project_index: pi, worktree_index: wi, depth });
                        dfs(pi, Some(worktrees[wi].name.as_str()), depth + 1, worktrees, children_of, entries, visited);
                    }
                }
            }
            let mut visited = std::collections::HashSet::new();
            dfs(pi, None, 0, &project.worktrees, &children_of, &mut entries, &mut visited); // ルート = parent:None
        }
    }
    entries
}
```

**防御的な循環対策** 🟡 *architecture.mdセクション7末尾の付記より*: `project.json` が外部改変等で循環を含んでいた場合に無限再帰しないよう、`visited: HashSet<usize>`（訪問済み `worktree_index`）を追加し、再訪問をスキップする。TASK-0003で `would_create_cycle` による事前ガードがあるため通常経路では発生しないが、防御的多層化として実装する。

**挿入順の安定性について** 🟡: `children_of` の各 `Vec<usize>` は `project.worktrees.iter().enumerate()` の順（= `Vec` の格納順）で `push` されるため、同じ親を持つ兄弟間の表示順は既存の `worktrees: Vec<Worktree>` の格納順が保たれる（`HashMap` のキー自体の非決定性は親の選択に影響するが、各キーに対応する子リストの中身の順序には影響しない）。回帰テスト（全worktreeが`parent=None`のケース）で、既存の単純ループと同じ順序になることを保証する根拠はここにある。

### 3. `is_last` を「兄弟内最後」に変更（`src/ui/left_panel.rs`） 🔵

**信頼性**: 🔵 *architecture.md セクション7、実地確認（`src/ui/left_panel.rs:131-133`）より*

現状（`src/ui/left_panel.rs:131-133`）：

```rust
let is_last = *worktree_index == app.projects[*project_index].worktrees.len() - 1;
```

これは「project内で物理的に最後のworktreeか」であり、階層化後は誤り（兄弟が他にいても、たまたま `Vec` の最後にいるだけの孫要素が `is_last=true` になってしまう）。「同じ親を持つ兄弟の中で最後か」に変更する必要がある。実装方針としては、`build_entries` が使う `children_of` マップと同じロジック（`wt.parent.as_deref()` で兄弟グループを求め、そのグループの最後の要素かを判定する）を `render` 側でも再構築するか、`ListEntry::Worktree` 構築時点で `is_last: bool` を追加のフィールドとして一緒に持たせる設計変更を検討してもよい 🟡 *interfaces.rsには`is_last`フィールド追記の明記はないため、`render`内での再計算が最小差分だが、`build_entries`内で一度計算した値を`ListEntry`に持たせて渡す方が二重計算を避けられ望ましい。いずれの実装を選ぶかは実装時の判断とする*。

### 4. インデントの depth 依存化（`src/ui/left_panel.rs`） 🔵

**信頼性**: 🔵 *architecture.md セクション7、実地確認（`src/ui/left_panel.rs:160`）より*

現状（`src/ui/left_panel.rs:160`）：

```rust
let prefix = format!("  {} ", branch_char);
```

これは常に固定2スペースの祖先インデントであり、`depth` を考慮していない。以下のように `depth` 依存に変更する：

```rust
let prefix = format!("{}{} ", "  ".repeat(entry_depth), branch_char); // 🔵 depthでインデント可変化
```

**`depth=0`（ルート）のケースで既存の見た目と完全一致すること** 🔵 が回帰安全性の要件（REQ-014は新規機能追加であり、既存の単一階層プロジェクトの表示を壊してはならない）。`"  ".repeat(0)` は空文字列になるため、`depth=0` の場合の出力は現行の `format!("  {} ", branch_char)` と一致する（`"  "` の位置が `repeat(0)` で消える分、`branch_char` の前に何もつかない差異が生じる可能性があるため、実装時に既存の「2スペース＋枝文字」の見た目を維持したい場合は `depth + 1` 回のrepeatにする等、既存出力とのバイト単位比較でテストし、必要に応じてオフセット調整すること）🟡 *architecture.mdのスニペットをそのまま使うと`depth=0`で字下げが1段減る可能性があり、回帰テストで実際の出力文字列を比較して確認が必要*。

## 基本的な単体テスト要件

**信頼性**: 🔵 *architecture.md セクション7、REQ-014より*

### build_entries: DFS順序とdepth

- **Given**: project内に A(parent=None), B(parent=Some("A")), C(parent=Some("B")) の3 worktree（Vec格納順は A, B, C）
- **When**: `build_entries(&[project])` を呼ぶ
- **Then**: 返り値の `Worktree` エントリが `[A(depth=0), B(depth=1), C(depth=2)]` の順で並ぶ

### build_entries: 階層なし（回帰安全性）

- **Given**: 全worktreeが `parent=None` の既存プロジェクト（例: X, Y, Z の3 worktree、フラット）
- **When**: `build_entries(&[project])` を呼ぶ
- **Then**: 出力される `worktree_index` の順序が変更前の単純ループ実装と完全一致し、全エントリの `depth` が `0` である

### is_last: 兄弟内最後の判定

- **Given**: A(parent=None) の子として B, C の2つ（B, Cが兄弟）、さらに独立worktree D（parent=None）
- **When**: 各エントリの `is_last` 相当判定を行う
- **Then**: `C`（Bの後に続く最後の子）が `is_last=true`、`B` は `is_last=false`。`D` は`A`の子ではなくルートグループの要素として、ルートグループ内での最後判定に従う

- **Given**: 単一の子 E のみを持つ親 F
- **When**: `E` の `is_last` を判定する
- **Then**: 唯一の子であるため `is_last=true`

### 防御的循環対策

- **Given**: 意図的に循環を仕込んだテストフィクスチャ（X.parent=Y, Y.parent=X）
- **When**: `build_entries` を呼ぶ
- **Then**: 無限再帰せず処理が終了する（`visited` セットにより2周目以降がスキップされる）
