## タスク概要

既存の `finalize_add_worktree`（`src/main.rs:2122-2223`、TUIのworktree追加ポップアップから呼ばれる関数）を、ポップアップ状態（`app.add_worktree_project_index`/`app.add_worktree_name` 等）に依存しない状態レス関数 `create_worktree_internal` として切り出す（REQ-022）。その上で、指揮者Claudeが自身配下に子worktreeを生成できる MCPツール `spawn_child_worktree` を追加する（REQ-023）。

**🔴 このタスクの本質的な難所**: `spawn_child_worktree` はMCPツールとして呼び出されるが、MCPツールは短命の別プロセス（`siki mcp`）で実行される。一方、worktree生成は実際に git コマンドを実行し、TUI本体プロセスがメモリ上に保持する `app.projects[pi].worktrees` を変更する必要がある。既存のMCPツール（`dispatch`, `send_message`, `broadcast` 等）は SQLite `messages` テーブルへのINSERTのみで完結し、TUI側は100ms Tickで非同期にポーリングするだけであり、この「MCPプロセス→TUI本体プロセスの生存中インメモリ状態への書き込み」を実現する前例は現状のコードベースに存在しない（mcp-tools.md 訂正・信頼性サマリー参照）。本タスクでは、後述の2案から実装時に選択し、選択した案の妥当性を実装しながら検証すること。

### 1. `create_worktree_internal` の切り出し（REQ-022） 🔵

**信頼性**: 🔵 *既存 `finalize_add_worktree`（main.rs:2122-2223）を実地確認済み、design-interview.mdの記述と一致*

現状の `finalize_add_worktree` は以下のシグネチャで、冒頭2行 `app.add_worktree_project_index`/`app.add_worktree_name` を読んで `pi`/`wt_name` を得ている:

これを次の形へ分離する:

```rust
/// worktree 作成のコア処理（状態レス）。ポップアップUI状態を一切読まない。
/// 呼び出し元は project_index / worktree_name を明示的に渡すこと（REQ-022）。
fn create_worktree_internal(
    app: &mut app::App,
    terminals: &mut HashMap<TerminalKey, terminal::TerminalEmulator>,
    event_tx: &tokio::sync::mpsc::UnboundedSender<event::AppEvent>,
    shell: &str,
    project_index: usize,
    worktree_name: &str,
    branch: &str,
    start_point: Option<&str>,
    no_track: bool,
    display_name: Option<&str>,
    parent: Option<&str>,                          // 🔵 新規: REQ-023
) -> Result<(), String> {
    let pi = project_index;
    let wt_name = worktree_name.to_string();

    let project_name = app.projects[pi].name.clone();
    let project_path = app.projects[pi].path.clone();
    let wt_path = config::worktree_path(&project_name, &wt_name);
    let shared_dirs = config::load_effective_shared_dirs(&project_name);

    if let Err(e) = git::WorktreeManager::create_worktree_from_ref(
        &project_path, &wt_path, branch, start_point, no_track, &shared_dirs,
    ) {
        return Err(format!("worktree の作成に失敗: {}", e));
    }

    app.projects[pi].worktrees.push(app::Worktree {
        name: wt_name.clone(),
        display_name: display_name.map(|s| s.to_string()),
        branch: branch.to_string(),
        path: wt_path.clone(),
        // ...既存フィールド初期化を維持（main.rs:2160-2179と同一）...
        pr: None,
        claude_session_id: None,
        context_items: Vec::new(),
        context_cursor: 0,
    });

    let wi = app.projects[pi].worktrees.len() - 1;
    let tx = event_tx.clone();
    let pr_path = wt_path.clone();
    tokio::spawn(async move {
        let info = fetch_pr_info(&pr_path).await;
        let _ = tx.send(event::AppEvent::PrInfo { worktree_id: (pi, wi), info });
    });

    if let Some(name) = display_name {
        if let Err(e) = config::save_worktree_display_name(&project_name, &wt_name, Some(name)) {
            app.show_error(format!("表示名の保存に失敗: {}", e));
        }
    }

    // 🔵 REQ-023: 親リンクの永続化（parentがSomeの場合のみ）
    if parent.is_some() {
        if let Err(e) = config::save_worktree_parent(&project_name, &wt_name, parent) {
            app.show_error(format!("親リンクの保存に失敗: {}", e));
        }
    }

    if let Some(siki_json) = config::load_effective_siki_json(&project_path, &project_name) {
        if let Some(ref setup_script) = siki_json.scripts.setup {
            run_siki_script(app, terminals, event_tx, shell, (pi, wi), setup_script, &wt_name, &wt_path);
        }
    }

    app.show_info(format!("worktree 追加完了: {} ({})", wt_name, branch));
    Ok(())
}
```

**既存 `finalize_add_worktree` は薄いラッパーへ**（ポップアップ状態の読み取りとUIリセットのみを担当）:

### 2. 🔴 MCPプロセス→TUI本体プロセスのブリッジ方式（未確定・実装時に選択）

**信頼性**: 🔴 *design-interview.md・mcp-tools.md 双方が「既存コードに前例がなく実装フェーズでの検証が必要」と明記している未解決事項。以下は選択肢の提示であり、どちらか一方を規定するものではない*

既存のMCPツール（`dispatch` を含む）はすべて「MCPプロセスがSQLiteにINSERTするだけ」で完結し、実際の副作用（PTYへの書き込み等）はTUI本体プロセスが100ms Tickで拾って行う。`spawn_child_worktree` はこのパターンに素直に乗せられる部分（git worktree作成、project.json書き込み）と、乗せにくい部分（`app.projects[pi].worktrees` へのインメモリpush、`claude_terms`との連携）が混在している。

#### 選択肢1: messagesテーブル + TUI側Tickハンドラでのブリッジ（dispatchパターンの転用）🟡 推奨

- MCPツールは `messages` テーブルへ `message_type='spawn_request'` の行をINSERTする。`content` には `{project, parent, branch, worktree_name}` をJSONエンコードして格納する。
- `AppEvent::Tick` ハンドラ（`main.rs:1677`以降、dispatch配送ロジックの追加箇所と同じ場所、TASK-0002で追加されたブロックの近傍）に新規分岐を追加し、未読の `spawn_request` 行をポーリングして `create_worktree_internal` を直接呼び出す（Tickは既にTUI本体プロセス内で動作しており `app`/`terminals` へのフルアクセスを持つため、これが可能）。
- 成功したら該当行を `mark_messages_read` で既読化する。MCPツール側は「投入した」ことのみを即座に返し（fire-and-forgetの非同期応答）、実際の生成完了は次回Tickで行われる。
- **利点**: dispatch機構（TASK-0001/0002）で既に実証済みのパターンをそのまま転用でき、新規IPC経路を発明する必要がない。NFR-001（既存100ms Tickへの集約）にも合致する。
- **懸念点** 🟡: MCPツールの呼び出し元（指揮者Claude）へ即座に返す応答に、生成された worktree_name や成功/失敗を含めることができない（Tick側で非同期に処理されるため）。指揮者Claude側は `list_sessions` や次回の確認ポーリングで生成完了を確認する運用になる可能性が高く、mcp-tools.mdが示す同期的な戻り値 `{"worktree": <生成された名前>, "parent": <親名>}` をそのまま返せない可能性がある。この点は実装時に「dispatchと同じ非同期応答にするか」「別の同期確認手段を用意するか」を確定すること。

#### 選択肢2: MCPプロセスからの直接処理（TUI状態には触れない）🔴

- MCPツールが `git::WorktreeManager::create_worktree_from_ref`（`app`を要求しないプレーンな関連関数）を直接呼び、worktreeのファイルシステム作成と `project.json` への親リンク書き込み（`config::save_worktree_parent`）をMCPプロセス内で完結させる。
- `app.projects`/`claude_terms` には一切触れない。実行中のTUIがこの新規worktreeを認識するには、既存の project/worktree discovery 機構（note.mdが言及する `discover_projects()`/`migrate_worktree_meta` 等、プロジェクトスキャン時に走る処理）に依存することになる。
- **🔴 実質的なギャップ**: 「TUI作成主体を経由せずworktreeが出現する」ケースへの既存の再スキャン・反映経路が現状のコードベースに存在するかどうかは本設計フェーズで確認できていない。存在しない場合、実行中のTUIセッションは siki 再起動まで新規worktreeを認識できず、完了条件「実行中のTUIセッションから可視・操作可能になる」を満たせない可能性がある。
- この案を選ぶ場合、実装者はまず既存コードに「外部要因でworktreeが増えたときにTUIへ反映する経路」があるかを調査し、無ければ本タスクの範囲内で最小限の反映トリガー（例: 左ペインフォーカス時の再スキャン、または明示的な `refresh` コマンド）を追加する必要がある。この追加分は当初のPhase 3見積り工数（8h）を超える可能性がある 🔴。

**推奨と実装時の指示**: 選択肢1（Tickベースのブリッジ）を第一候補として推奨する。理由は、dispatch機能（TASK-0001/0002）で既に検証済みの構造を再利用でき、新規の状態同期機構を発明しないで済むため。ただし、この推奨は設計段階の判断であり実装時に検証されていない。実装着手時に、選択肢1が現在の `main.rs` 構造（Tickハンドラの実装、`app`/`terminals`への可変参照の取り回し）に対して本当に無理なく組み込めるかを最初に確認し、問題があれば選択肢2、または両者のハイブリッド（生成はTick経由・親リンクの即時書き込みのみMCP側で先行実施等）を検討すること。いずれを選んでも、選択した理由と既知のギャップ（特に選択肢2の場合の再スキャン未実装リスク）をPR説明に明記すること。

## 基本的なテスト要件

### 単体テスト 🔵

**信頼性**: 🔵 *完了条件・REQ-022, REQ-023より*

- `create_worktree_internal` がポップアップ状態（`app.add_worktree_project_index`/`app.add_worktree_name`）を一切参照せず、明示的な引数のみで呼び出し可能であること（コンパイル時に保証されるが、テストでも「ポップアップ状態を設定せずに呼んでも動く」ケースを用意する）
- `parent: Some("A")` を渡した場合、worktree作成成功後に `config::save_worktree_parent` が呼ばれ、`project.json` の該当worktreeの `parent` フィールドが `"A"` になること
