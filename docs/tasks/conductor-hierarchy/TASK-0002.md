### 2. `App::find_worktree_id` 🔵

**信頼性**: 🔵 *architecture.md セクション5、design-interview.md訂正2: `resolve_worktree_id`相当の関数はコードベースに存在しないため新規実装が必要と確認済み（実地確認: `src/app.rs` に `find_worktree_id` は未実装、`grep` で該当なし）*

`src/app.rs` の `impl App`（`App` 構造体は `app.rs:269-` 、`projects: Vec<Project>` を持つ）へ以下を追加する。

```rust
impl App {
    /// (project_name, worktree_name) から現在の WorktreeId を解決する（REQ-002）。
    /// WorktreeId は add/remove で再インデックスされ不安定なため、呼び出しの都度解決すること
    /// （キャッシュしてはならない）。
    pub fn find_worktree_id(&self, project_name: &str, worktree_name: &str) -> Option<WorktreeId> {
        self.projects.iter().enumerate().find_map(|(pi, p)| {
            if p.name != project_name {
                return None;
            }
            p.worktrees
                .iter()
                .position(|w| w.name == worktree_name)
                .map(|wi| (pi, wi))
        })
    }
}
```

`WorktreeId` は `app.rs:11` で `pub type WorktreeId = (usize, usize);` として定義済み（実地確認）。

### 3. `dispatch_retry_counts` とリトライ上限の宣言 🔵

**信頼性**: 🔵 *architecture.md セクション5、design-interview.md Q1・Q2、実地確認 `main.rs:185`（`claude_terms` の宣言箇所）*

`claude_terms`（`main.rs:185`、`main()` 関数のイベントループ用ローカル変数）と同じスコープに以下を追加する。

```rust
let mut dispatch_retry_counts: HashMap<i64, u32> = HashMap::new(); // dispatch_id -> リトライ回数
const DISPATCH_RETRY_LIMIT: u32 = 30; // Q1: 約3秒(100ms×30)
```

**実装メモ（スコープを跨ぐ配線が必要）** 🔵: `AppEvent::Tick` のマッチアームは `main()` 内ではなく、実地確認の結果 `async fn handle_event(...)`（`main.rs:384`〜、`claude_terms: &mut HashMap<...>` を引数として受け取る）内の `AppEvent::Tick => { ... }`（`main.rs:1677-1717`）に存在する。`claude_terms` は `main()` で宣言され `&mut` 参照として `handle_event` へ渡されている（`main.rs:343`, `360` 等の呼び出し箇所を参照）。`dispatch_retry_counts` も同様に `main()` で宣言し、`handle_event` のシグネチャへ新規引数 `dispatch_retry_counts: &mut HashMap<i64, u32>` を追加し、全呼び出し箇所（`main.rs:343`, `360` 他、`handle_event` を呼ぶ全ロケーション）を更新する必要がある。呼び出し箇所を網羅的に更新すること（`cargo build` のコンパイルエラーで漏れを検出できる）。

### 4. Tick処理への配送ロジック追加（`src/main.rs` `AppEvent::Tick`） 🔵

**信頼性**: 🔵 *architecture.md セクション5、実地確認 `main.rs:1677-1717`（既存のアラート同期ブロックの直後に追記）*

既存の `AppEvent::Tick` ハンドラの末尾（DB→インメモリのアラート状態同期ブロック、`main.rs:1708-1716` の直後、`main.rs:1717` の閉じ括弧の手前）に配送ロジックを追加する。

```rust
AppEvent::Tick => {
    // ...既存の処理（app.clear_expired_status() 〜 アラート状態同期）...

    // dispatch配送（REQ-002〜006）
    if let Ok(conn) = broker_db.lock() {
        if let Ok(dispatches) = db::get_pending_dispatches(&conn) {
            for d in dispatches {
                let (Some(to_wt), Some(to_proj)) = (&d.to_worktree, &d.to_project) else { continue }; // 不整合行は無視
                let resolved = app.find_worktree_id(to_proj, to_wt)          // 新規実装(上記2節)
                    .and_then(|wt_id| claude_terms.get_mut(&(wt_id, 0)).map(|emu| (wt_id, emu)));

                match resolved {
                    Some((_wt_id, emu)) if emu.is_alive() => {                // is_alive()必須（write()は非aliveでもOkを返すため）
                        let msg = format!("{}\n", d.content);
                        if emu.write(msg.as_bytes()).is_ok() {
                            let _ = db::mark_messages_read(&conn, &[d.id]);    // 既存関数を再利用
                            dispatch_retry_counts.remove(&d.id);
                        }
                        // write失敗時は既読化しない → 次Tickで再度この分岐に到達しリトライされる
                    }
                    _ => {
                        // 対象worktreeが存在しない(EDGE-001) または PTY未生成・非aliveの場合(REQ-005)
                        let count = dispatch_retry_counts.entry(d.id).or_insert(0);
                        *count += 1;
                        if *count >= DISPATCH_RETRY_LIMIT {
                            let _ = db::mark_messages_read(&conn, &[d.id]);
                            dispatch_retry_counts.remove(&d.id);
                            // REQ-006: set_alert相当の人間向け通知（既存 app.show_error の枠組みを利用）
                            app.show_error(format!(
                                "dispatch配送に失敗しました（{}回リトライ後に断念）: {} -> {}",
                                DISPATCH_RETRY_LIMIT, to_proj, to_wt
                            ));
                        }
                    }
                }
            }
        }
    }
}
```

`app.show_error` は実地確認済みの既存メソッド（`src/app.rs:582`、`pub fn show_error(&mut self, message: String)`）を利用する。新規実装は不要。

**REQ-004（working状態でも即時投入）** 🔵: 上記ロジックにはセッション状態（idle/working）で分岐する箇所が一切ない。`claude_terms` にエントリがあり `is_alive()` であれば無条件で即時 `write()` する。working時に投入を待機させる専用キューは実装しない（要件通り）。

**REQ-005/EDGE-001の経路統合** 🔵 *dataflow.md 機能2の備考より*: `find_worktree_id` が `None` を返すケース（対象worktree不存在、EDGE-001）と、`claude_terms` にエントリがない/非aliveのケース（PTY未生成、REQ-005）は、上記コードの `_ =>` という同一のマッチアームで扱われる。これは設計文書で明示された意図的な統一であり、両ケースを区別する追加分岐は実装しない。

**EDGE-101（境界値）** 🔵: `*count += 1` の直後に `*count >= DISPATCH_RETRY_LIMIT` を判定するため、30回目のTickでカウントが30に到達した瞬間にアラート・既読化が行われ、以降（31回目のTick）ではこの `dispatch_id` はDBから既に取得されない（`get_pending_dispatches` の `WHERE read_at IS NULL` に一致しなくなるため）。

## 単体テスト要件

`main.rs` の `AppEvent::Tick` ハンドラは多数の引数（`app`, `claude_terms`, `broker_db`, `dispatch_retry_counts` 等）を要し、直接の単体テストが書きにくい。したがって以下の2方針で分離してテストする。

### 方針A: 純粋ロジックとして独立に検証可能な部分（推奨）

配送1件分の「成功/リトライ増加/上限到達」判定ロジックを、`TerminalEmulator`・DB接続への依存を最小化した小さい純粋関数（例: `fn decide_dispatch_action(is_resolved: bool, is_alive: bool, write_ok: bool, retry_count: u32, limit: u32) -> DispatchAction` のようなヘルパー、戻り値は `enum DispatchAction { MarkReadAndClear, IncrementRetry, MarkReadAndAlert }` 等）へ切り出せないか実装時に検討する。切り出せた場合は以下をテストする（あくまで実装上の提案であり、必須要件ではない）:

- **Given** `is_resolved=true, is_alive=true, write_ok=true`
  **When** 判定関数を呼ぶ
  **Then** `MarkReadAndClear` が返る
- **Given** `is_resolved=false`（対象未解決、EDGE-001） かつ `retry_count=0`
  **When** 判定関数を呼ぶ
  **Then** `IncrementRetry`（カウントが1になる）が返る
- **Given** `is_resolved=true, is_alive=false`（REQ-005: PTY未生成/非alive） かつ `retry_count=29`
  **When** 判定関数を呼ぶ
  **Then** カウントが30になり `MarkReadAndAlert` が返る（EDGE-101境界）
- **Given** `retry_count=30`（既に上限）到達済みの状態が次Tickに残ることはない
  **Then** 上限到達と同時に既読化される設計のため、この状態は再現不可能であることをテストで確認（回帰防止）

切り出しが困難と判断した場合は、実装時にその旨をコードコメントで明記し、下記「統合/手動テスト」で代替検証する。

### `find_worktree_id` 単体テスト 🔵

- **Given** `App` に project `"proj-a"` の下に worktree `"child-1"`, `"child-2"` を持つ `Project`/`Worktree` を構築した状態
  **When** `app.find_worktree_id("proj-a", "child-2")` を呼ぶ
  **Then** `Some((0, 1))` のような正しい `WorktreeId` が返る
- **Given** 上記と同じ `App`
  **When** `app.find_worktree_id("proj-a", "unknown")` または `app.find_worktree_id("unknown-proj", "child-1")` を呼ぶ
  **Then** `None` が返る
- **Given** 同名projectが存在しない、または `projects` が空の `App`
  **When** `find_worktree_id` を呼ぶ
  **Then** `None` が返る（パニックしない）

### リトライカウンタの増減 🔵

- **Given** `dispatch_retry_counts` が空の `HashMap<i64, u32>`
  **When** ある `dispatch_id` に対して「未解決」処理を1回シミュレートする
  **Then** `dispatch_retry_counts.get(&dispatch_id) == Some(&1)`
- **Given** ある `dispatch_id` の書き込みが成功した
  **When** 成功処理をシミュレートする
  **Then** `dispatch_retry_counts` から当該 `dispatch_id` のエントリが削除されている（`remove` 済み）
