### 2. `move_worktree` 関数 + ディスパッチ（`src/mcp/tools.rs`） 🔵

**信頼性**: 🔵 *mcp-tools.md 実装概要をそのまま転記、REQ-012, REQ-015より*

`execute_tool`（`src/mcp/tools.rs:10`〜）の `match tool_name` に `"move_worktree" => move_worktree(conn, params, session_id),` を追加し、以下を実装する：

```rust
fn move_worktree(conn: &Connection, params: &Value, from_session: &str) -> Result<Value> {
    let child = params.get("child").and_then(|v| v.as_str())
        .ok_or_else(|| anyhow::anyhow!("child is required"))?;
    let parent = params.get("parent").and_then(|v| v.as_str()); // null/欠落 → None

    // 呼び出し元セッションの project_name を自己解決
    // （既存 list_sessions の自己参照パターン、tools.rs:37-43 と同型）
    let all_sessions = db::list_sessions(conn)?;
    let project_name = all_sessions.iter()
        .find(|s| s.session_id == from_session)
        .map(|s| s.project_name.clone())
        .ok_or_else(|| anyhow::anyhow!("caller session not found"))?;

    if let Some(p) = parent {
        if config::would_create_cycle(&project_name, child, p) {  // REQ-015
            anyhow::bail!("circular parent link: {} -> {}", child, p);
        }
    }
    config::save_worktree_parent(&project_name, child, parent)?;

    Ok(json!({ "child": child, "parent": parent }))
}
```

**戻り値**: `{"child": <名前>, "parent": <名前 or null>}` 🟡 *mcp-tools.mdより、既存ツールのレスポンス慣習からの推測であり確定仕様ではない*

**呼び出し元projectの自己解決について** 🔵: `resolve_own_project` のような共通ヘルパー関数は現時点の実装コードに存在しない（`list_sessions`, `dispatch`（TASK-0001実装時点）のいずれも各関数内でインライン実装している）。本タスクでも同型のインライン実装で構わないが、もし TASK-0001/0002 で `resolve_own_project` 相当の共通関数が既に切り出されていれば、それを再利用すること 🟡 *TASK-0001/0002実装内容は本タスク作成時点で未実装のため実装順序依存*。

### 4. EDGE-102（cross-project移動の拒否）は構造上の帰結 🔵

**信頼性**: 🔵 *mcp-tools.md「cross-project制約」、architecture.md記載より*

`move_worktree` は呼び出し元セッションの `project_name` を自己解決した上で、その `project_name` に対してのみ `config::would_create_cycle`/`config::save_worktree_parent` を呼ぶ。これらの関数は内部で `config::load_project_meta(project_name)` により**当該project.jsonのみ**を読み書きするため、`child`/`parent` に他projectのworktree名を指定しても、そのproject.json内に存在しない名前として扱われるだけであり、意図しないcross-project付け替えは構造上発生しない。**追加の検証コードは不要**であり、設計から自然に導かれる性質である 🔵。ただし、この前提が壊れていないことを確認する回帰テストは追加すること（下記テスト要件参照）。

## 基本的な単体テスト要件

**信頼性**: 🔵 *mcp-tools.md エラーケース、REQ-012, REQ-015, EDGE-102より*

### move_worktree: 正常系

- **Given**: 独立worktree `child` と 別worktree `parent`（同一project内）
- **When**: `move_worktree({child: "child", parent: "parent"})` を呼ぶ
- **Then**: 戻り値が `{"child": "child", "parent": "parent"}`、かつ `config::load_worktree_meta(project, "child").parent == Some("parent")`

### move_worktree: 循環拒否

- **Given**: `child` 自身
- **When**: `move_worktree({child: "X", parent: "X"})`（自己参照）を呼ぶ
- **Then**: エラーが返り、`save_worktree_parent` は呼ばれない（`load_worktree_meta` の `parent` が変化しないことで検証）

- **Given**: A(parent=None) ← B(parent=A) ← C(parent=B) のチェーン
- **When**: `move_worktree({child: "A", parent: "C"})`（Aの子孫であるCをAの親にしようとする推移的循環）を呼ぶ
- **Then**: エラーが返り、`A` の `parent` は変化しない

### move_worktree: 独立化（detach）

- **Given**: `parent: Some("A")` を持つ worktree `B`
- **When**: `move_worktree({child: "B", parent: null})` を呼ぶ
- **Then**: `B` の `parent` が `None` になる

### move_worktree: cross-project構造的拒否（EDGE-102）

- **Given**: project `P1` に worktree `X`、project `P2` に worktree `Y`（同名衝突なし）
- **When**: `P1` の呼び出し元セッションから `move_worktree({child: "Y", parent: "X"})` を呼ぶ（`Y` は `P1` のproject.jsonには存在しない）
- **Then**: `P1` のproject.jsonに `Y` というエントリが新規作成される（`entry().or_default()` の挙動）としても、`P2` 側の `Y` の実体には一切影響しない。理想的には「`child` が呼び出し元project内の実在worktreeでない場合はエラーにする」という追加の存在チェックを推奨する 🟡 *mcp-tools.md「エラーケース」に記載の通り、現状の設計は存在チェックをHashMapエントリ操作に委ねており明示的な検証がないため、本タスクで存在チェックを追加するか判断すること*

### TUIキー操作

- **Given**: 左ペインで子worktreeにカーソルがある状態
- **When**: 新規キーバインドで付け替え操作を実行する
- **Then**: 内部的に `config::would_create_cycle` → `config::save_worktree_parent` と同じ経路を通り、次回描画時のツリー（`LeftPanel::build_entries`）に反映される
