# worktree削除時のインデックス整合性修正 ヒアリング記録

**作成日**: 2026-07-01
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング（フル機能開発）

## ヒアリング目的

直前の会話でのコード調査により、worktree 削除時に別 worktree のタブがフリーズする不具合
（Bug A）を確認済みだった。加えて調査の過程で、id 照合のない別経路（Bug B）と、プロジェクト
削除時の未実装 reindex（Bug C）という関連する2つの問題を発見した。要件のスコープ・修正方針・
互換性方針・テスト方針・未解決時の挙動・モーダル系フィールドの扱いを確定するためヒアリングを
実施した。

## 質問と回答

### Q1: 今回の要件に含める不具合はどれか（複数選択可）

**質問日時**: 2026-07-01
**カテゴリ**: 優先順位・スコープ調整
**背景**: コード調査で Bug A（再現確認済み）に加え Bug B・Bug C（コード調査のみ、未実発生
確認）を発見したため、スコープに含めるかどうかの判断が必要だった。

**回答**: すべて含める（A: PTY/Claudeタブのフリーズ、B: ClaudeSession経由の内容差し替わり、
C: プロジェクト削除時の連鎖ズレ）

**信頼性への影響**:
- REQ-002, REQ-006（Bug B対応）、REQ-102（Bug C対応）を要件として追加し、信頼性レベルを
  🔵（ヒアリングで確定）とした

---

### Q2: 修正方針として「グローバル一意 id による解決方式」で進めてよいか

**質問日時**: 2026-07-01
**カテゴリ**: 既存設計の妥当性・過不足確認
**背景**: `TerminalEmulator` には既に `id: u64` があり Claude タブの一部で id 照合が使われて
いるが、`terminals`（通常ターミナル）と `ClaudeSession` には同等の仕組みがない。reindex を
より徹底する方式との比較検討が必要だった。

**回答**: 提案方式（id解決）で進める

**信頼性への影響**:
- REQ-001〜REQ-006 の技術方針を id ベース解決に確定し、信頼性レベルを 🔵 に確定

---

### Q3: `AppEvent`/`ClaudeSession` への新規フィールド追加など内部プロトコル変更は許容できるか

**質問日時**: 2026-07-01
**カテゴリ**: 既存機能への影響範囲確認
**背景**: id ベース解決には `ClaudeSession` への `id` フィールド追加、`AppEvent` への
`session_id` フィールド追加が必要になるため、内部プロトコル変更の許容度を確認する必要が
あった。

**回答**: 許容する

**信頼性への影響**:
- REQ-403（制約要件）を 🔵 で追加。実装対象メモに `event.rs`/`claude.rs` の変更を明記

---

### Q4: 再発防止のためのテスト整備（ユニットテスト・回帰テスト）を含めるか

**質問日時**: 2026-07-01
**カテゴリ**: 優先順位・スコープ調整
**背景**: 本不具合はバックグラウンドタスクの非同期タイミングに依存するため、目視確認だけでは
再発を防ぎにくい。テスト整備の要否を確認した。

**回答**: 修正+再発防止テスト（推奨）

**信頼性への影響**:
- 受け入れ基準（acceptance-criteria.md）にユニットテスト観点のテストケースを含めることを確定

---

### Q5: id 一致でも実体が見つからない場合の挙動（現行=黙って drop）は維持でよいか

**質問日時**: 2026-07-01
**カテゴリ**: 未定義・曖昧部分の詳細化ヒアリング
**背景**: タブが正常に閉じられた後に届く遅延イベント等、正常系でも id 不一致は起こり得る
ため、ログ出力を追加すべきかどうかの判断が必要だった。

**回答**: 現行通り黙って drop（推奨）

**信頼性への影響**:
- REQ-401（制約要件）を 🔵 で追加し、ログ出力機能は要件に含めないことを明確化

---

### Q6: `archive_target`/`rename_worktree_target`/`session_choice_wt_id`/`llm_picker_wt_id`
等モーダル系 `WorktreeId` 保持フィールドの扱い

**質問日時**: 2026-07-01
**カテゴリ**: 既存機能への影響範囲確認
**背景**: これらのフィールドも `WorktreeId` を保持するため理論上は同種の問題を持ちうるが、
TUI の構造上同時に複数モーダルが開くことはなく、リスクは低いと推定していた。

**回答**: 今回は対象外（推奨）

**信頼性への影響**:
- REQ-402（制約要件）を 🔵 で追加し、明示的にスコープ外と記載

---

## ヒアリング結果サマリー

### 確認できた事項
- Bug A（PTY/Claude タブのフリーズ）はユーザー環境で実際に再現し、原因はコード調査で特定済み
- Bug B・Bug C はコード調査により実装上の欠陥として確認されたが、実発生の目撃報告は未確認
- 修正方針は「グローバル一意 id による実体解決」に統一し、内部プロトコル変更も許容
- テスト整備を今回のスコープに含める
- モーダル系フィールドとログ追加は明示的にスコープ外

### 追加/変更要件
- REQ-002, REQ-004, REQ-005, REQ-006（Bug A/B 対応の中核）
- REQ-102, REQ-103（Bug C 対応）
- REQ-401, REQ-402, REQ-403（制約・スコープ確定）

### 残課題
- Bug B・Bug C は実発生の一次情報がなく、設計・実装フェーズでの回帰テストによる検証が
  信頼性を担保する主な手段になる
- id 解決ヘルパーの共通化度合い（`terminals`/`claude_terms`/`sessions` で完全共通化するか、
  型ごとに個別実装するか）は `/tsumiki:kairo-design` で詳細化する
