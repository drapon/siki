# エージェント監視システム 要件定義書

## 概要

siki の TUI 上で「どのプロジェクトの、どの worktree で、どのエージェントが、今/直前に何をしているか」をリアルタイムに俯瞰できる監視機能を追加する。

現状、Claude Code の hook（PreToolUse / PostToolUse / PermissionRequest / Stop / SessionEnd）は broker 経由でセッション状態（working/waiting/done/idle）を収集し、左ペインのバッジ（●/○）に反映しているが、(1) ツール単位の活動内容（何のツールを実行中か）は hook で捨てられており、(2) 個々のエージェントの活動をまとめて閲覧する画面が存在しない。

本要件では、hook を拡張してツール単位のアクティビティ（例:「Bash: bun test」「Edit: session.rs」）を取得・保持し、左ペインから専用ホットキーで開く2つのビュー（① プロジェクト別ポップアップ ② 全プロジェクト横断ダッシュボード）で表示する。表示中はセッション状態の変化に追従してリアルタイムに更新される。

## 機能要件（EARS記法）

**【信頼性レベル凡例】**:
- 🔵 **青信号**: 設計文書・コードベース調査・ユーザヒアリングを参考にした確実な要件
- 🟡 **黄信号**: 設計文書・コードベース調査・ユーザヒアリングから妥当な推測による要件
- 🔴 **赤信号**: 上記資料にない推測による要件

### 通常要件

- REQ-001: システムは、各 Claude Code セッションについて、現在または直前に実行中のツール活動（activity）を取得し保持しなければならない 🔵 *ヒアリング（粒度=レベルB）*
- REQ-002: システムは、PreToolUse hook が渡す `tool_name` と `tool_input` から、人間可読な1行の activity 文字列を生成しなければならない 🔵 *ヒアリング・`hook_event.rs:51`*
- REQ-003: システムは、左ペインで `m` キーが押されたとき、カーソル位置に対応するプロジェクトに属する worktree/エージェントの活動状況を示すポップアップを表示しなければならない 🔵 *ヒアリング（トリガー=m）*
- REQ-004: システムは、`M`（Shift+m）キーが押されたとき、全プロジェクトを横断してエージェント活動を一覧する全体ダッシュボードを表示しなければならない 🔵 *ヒアリング（スコープ=両方）*
- REQ-005: システムは、両ビューの各エージェント行に activity・summary・role・state・最終更新からの経過時間を表示しなければならない 🔵 *ヒアリング（表示項目）*
- REQ-006: システムは、全体ダッシュボードのエントリを状態優先順（waiting > working > done > idle）で並べ替えて表示しなければならない 🔵 *ヒアリング（ダッシュ表示=状態優先順）*

### 条件付き要件

- REQ-101: セッション状態が変化した場合（broker からの `AppEvent::SessionUpdate` 受信時、および 100ms Tick 時）、表示中の監視ビューはその内容をリアルタイムに更新しなければならない 🔵 *`broker.rs`・Explore 調査*
- REQ-102: working（PreToolUse）イベントを受信した場合、システムは該当セッションの activity を新しいツール活動で更新しなければならない 🔵 *ヒアリング・`broker.rs:149`*
- REQ-103: PostToolUse（refresh）や Stop（idle）の後も、システムは直前の activity を保持し表示し続けなければならない 🔵 *ヒアリング（activity=直前を残す）*
- REQ-104: セッションに alert（要人間対応: 許可待ち waiting または set_alert）がある場合、ビューは該当行を赤系の配色で強調表示しなければならない 🔵 *ヒアリング（alert強調）・`session.rs:263`*
- REQ-105: 監視ビューが表示されている状態で `Esc` が押された場合、システムはそのビューを閉じなければならない 🔵 *既存ポップアップパターン*
- REQ-106: `m` 押下時にカーソルが worktree 行にある場合、システムはその worktree が属するプロジェクトのポップアップを表示してもよい 🟡 *UX上の妥当な推測（プロジェクト行限定だと worktree 選択中に開けない）*

### 状態要件

- REQ-201: 監視ビューが表示されている間、システムは左/中/右ペインの通常キー操作を横取りし、ビュー専用キー（Esc・スクロール等）のみを処理しなければならない 🔵 *既存ポップアップパターン（早期 return）*
- REQ-202: 対象にアクティブなセッションが存在しない場合、ビューは「アクティブなエージェントなし」を示すメッセージを表示しなければならない 🟡 *UX上の妥当な推測*

### オプション要件

- REQ-301: システムは、監視ビュー内で項目数が表示領域を超える場合に、カーソル移動またはスクロール（`j`/`k`）を提供してもよい 🟡 *既存ポップアップ（help/llm picker）の慣習からの推測*

### 制約要件

- REQ-401: hook の broker 送信 payload は後方互換を保たねばならない。activity は optional フィールド（serde `default`）として既存 `working` イベントと共存させること 🔵 *note.md・`hook_event.rs`*
- REQ-402: sessions テーブルへの activity カラム追加は、既存の冪等な `ALTER TABLE ... ADD COLUMN` マイグレーションパターンに従わねばならない 🔵 *`db.rs:49-60`*
- REQ-403: activity 抽出・送信処理は、状態系 hook の stdin 読み取りタイムアウト（1s）と broker タイムアウトの合計が hook timeout（5s）を下回る制約を侵してはならない 🔵 *`hook_event.rs:9-23`*
- REQ-404: 実装はプロジェクト規約（日本語コメント・YAGNI・単一責任=1ファイル800行以内・イミュータブル志向・エラーの文脈付きハンドリング）に従わねばならない 🔵 *CLAUDE.md・coding-style.md*

## 非機能要件

### パフォーマンス

- NFR-001: 状態変化から監視ビューへの反映は 1 秒未満でなければならない（既存 broker 経路の特性を維持） 🔵 *`broker.rs`*
- NFR-002: ビューの描画処理は 100ms Tick の再描画予算内に収め、TUI 全体の応答性を損なってはならない 🟡 *既存 Tick レートからの妥当な推測*

### セキュリティ

- NFR-101: activity に含めるコマンド文字列等は表示・ローカル保持（インメモリ + SQLite）のみとし、外部へ送信してはならない 🔵 *既存アーキテクチャ（ローカル完結）*
- NFR-102: cwd 由来の project/worktree 名は既存のパストラバーサル防御（`is_safe_segment`）を踏襲しなければならない 🔵 *`session.rs:413`*

### ユーザビリティ

- NFR-201: トリガーキー（`m` / `M`）と `Esc` での閉操作は、ヘルプ（`?`/`F1`）に記載しなければならない 🔵 *README キーバインド表・既存 help 実装*
- NFR-202: activity・summary は表示幅に応じて省略表示（…）し、行崩れを起こしてはならない 🟡 *TUI 一般則からの妥当な推測*

## Edgeケース

### エラー処理

- EDGE-001: `tool_input` が想定キー（`command` / `file_path` / `description` 等）を欠く場合、システムは `tool_name` のみで activity を生成しなければならない 🟡 *Claude Code hook payload の多様性からの推測*
- EDGE-002: `tool_input` の値に改行・制御文字を含む場合、システムは1行に正規化（改行除去・トリム）しなければならない 🟡 *表示崩れ防止の妥当な推測*
- EDGE-003: cwd が空で自動登録された未知セッション（project/worktree が "unknown"）について、ダッシュボードでの表示方針を定めなければならない（許容して表示 or 抑制） 🟡 *`session.rs:354` の自動登録挙動からの推測*

### 境界値

- EDGE-101: 同一 worktree に複数のエージェントセッションが存在する場合、システムは各セッションを個別行で表示しなければならない 🔵 *`session.rs:203` `by_worktree` が複数返す*
- EDGE-102: activity 文字列が表示領域より長い場合、末尾を省略記号（…）で切り詰めなければならない 🟡 *NFR-202 由来*
- EDGE-103: セッション数が監視ビューの表示行数を超える場合、スクロールまたはページングで全件を閲覧可能にしなければならない 🟡 *REQ-301 由来*
