# エージェント監視システム ヒアリング記録

**作成日**: 2026-06-22
**ヒアリング実施**: step4 既存情報ベースの差分ヒアリング（および要件初期化時のスコープ確認）

## ヒアリング目的

PRD は存在せず、要件の発端はユーザーからの口頭要望（「全体でエージェントの動きを把握する画面が欲しい。左ペインのプロジェクト名から開いて、その中のエージェントが何をしているかをリアルタイムに見たい」）であった。既存コードベース（hook_event / session / broker / db / UI）を調査した上で、実装方針を確定するためのヒアリングを実施した。

## 質問と回答

### Q1: 表示する「何をしているか」の粒度

**質問日時**: 2026-06-19
**カテゴリ**: 未定義部分詳細化
**背景**: hook イベントは現状 `session_id` のみ抽出し、PreToolUse の `tool_name`/`tool_input` を捨てている（`hook_event.rs:51`）。「何をしているか」をツール単位まで出すには hook 拡張が要る。状態+要約のみ（hook 改修なし）か、ツール単位（hook 拡張あり）かで実装規模が変わる。

**回答**: レベルB（ツール単位）。hook を拡張し、PreToolUse の tool_name/tool_input を保存して「Bash: bun test」「Edit: auth.rs」のように表示する。

**信頼性への影響**:
- REQ-001・REQ-002・REQ-102 の信頼性を 🔵 に確定。hook 拡張を含むスコープが確定した。

### Q2: ポップアップを開くトリガー

**質問日時**: 2026-06-19
**カテゴリ**: 未定義部分詳細化

**回答**: 専用ホットキー方式を採用。

**信頼性への影響**:

### Q5: トリガーキーの具体割り当て

**質問日時**: 2026-06-22
**カテゴリ**: 既存設計確認 / 未定義部分詳細化
**背景**: README のキーバインド表を確認した結果、左ペインでは `Enter`（worktree選択）・`A`（プロジェクト追加）・`a`（worktree追加）・`Space`（開閉）が、中央では `i`/`g` が使用済み。当初案の Enter/A は流用不可と判明した。

**回答**: `m` = 選択中プロジェクトのポップアップ、`M`（Shift+m）= 全体ダッシュボード（monitor の連想）。

**信頼性への影響**:
- REQ-003・REQ-004 のトリガーキーを 🔵 に確定。既存キーとの衝突リスクを解消。

## ヒアリング結果サマリー

### 確認できた事項
- 状態収集経路（hook → broker → registry/DB → TUI）は既に整備済みで、リアルタイム反映の土台は揃っている。
- 「何をしているか」のツール単位情報は hook 拡張で取得する（レベルB）。
- トリガーは専用ホットキー `m`/`M`（既存キーと非衝突）。
- per-project ポップアップと全体ダッシュボードの両方を実装する。
- activity は完了後も直前を保持。ダッシュボードは状態優先順で全件表示。

### 追加/変更要件
- hook payload に activity（optional）を追加（REQ-401）。
- sessions テーブルに activity カラムを追加（REQ-402）。
- 当初の cmd+click 案 → 専用ホットキーへ変更（Q2）。
- 当初の Enter/A 案 → m/M へ変更（Q5、既存キー衝突回避）。

### 残課題
- EDGE-003: cwd 空の "unknown" セッションをダッシュボードで表示するか抑制するか（design フェーズで決定）。
- REQ-301/EDGE-103: スクロール/ページングの要否は項目数次第（design フェーズで具体化）。
- activity 文字列の整形ルール（ツール別フォーマット）の細部は design フェーズで確定。
