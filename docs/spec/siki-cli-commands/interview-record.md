## ヒアリング目的

既存コード（`src/main.rs` のディスパッチ・`launch_llm_with_args`・`src/git.rs`・`src/config.rs`・
`src/session_start.rs`）の調査結果をもとに、CLI 化の範囲と挙動の分岐点を確定するためのヒアリングを実施した。

## 質問と回答

### Q1: CLI でどこまで賄いたいか（スコープ）

**カテゴリ**: スコープ調整
**背景**: worktree 管理のみか、Claude セッション起動まで含むかで分離コストが大きく変わる
（後者は PTY/broker/TUI に結合）。

**回答**: **B（worktree 管理 + セッション起動まで）**

**信頼性への影響**: REQ-003〜004 を確定要件として追加（🔵）。

---

### Q2: run が起動した Claude セッションを TUI 本体はどう扱うべきか

**カテゴリ**: 未定義部分の詳細化
**背景**: broker 埋め込みでライブ監視するか、監視なしで前面 exec するかで実装の重さが変わる。

**回答**: **監視なし・前面 exec（推奨）**

**信頼性への影響**: REQ-402（broker 非起動でも DB 経由で状態復元）・スコープ外項目を確定（🔵）。
broker は複数セッションを束ねる TUI のための仕組みであり、単一の前面セッションには不要、という設計判断を裏付けた。

---

### Q3: ワンショット（`-p` で結果だけ受け取る非対話実行）を入れるか

**カテゴリ**: 追加要件
**背景**: 既存 `ClaudeSession`(src/claude.rs:22) の stream-json 経路を流用すれば CI/スクリプト向けに追加可能。

**回答**: **対話のみ（推奨/YAGNI）**

**信頼性への影響**: ワンショットをスコープ外として明記（🔵）。

---

### Q4: `siki new` のブランチ名

**カテゴリ**: 未定義部分の詳細化
**背景**: worktree 名とブランチ名を同一にするか、別指定可能にするか。

**回答**: **worktree 名と同名（推奨）**

**信頼性への影響**: REQ-002 を確定（🔵）。`--branch` 別指定は不採用。

---

### Q5: `siki run` で worktree が未作成のときの振る舞い

**カテゴリ**: 未定義部分の詳細化
**背景**: 自動作成して起動するか、エラーで `siki new` を促すか。

**回答**: **自動作成して起動（推奨）**

**信頼性への影響**: REQ-004 を確定（🔵）。

---

### Q6: 作業規模

**カテゴリ**: スコープ調整
**背景**: 薄い CLI ラッパで設計は既に明確。

**回答**: **軽量開発（推奨）**

**信頼性への影響**: 出力を requirements.md + interview-record.md の2点に限定。EARS フル展開はしない。

## ヒアリング結果サマリー

### 確認できた事項
- スコープは B（管理 + 起動）、run は監視なし前面 exec、対話のみ
- `siki new` のブランチ名は worktree 名と同名、base は resolve_base_branch を no_track で
- run は worktree 不在時に自動作成

### 追加/変更要件
- REQ-003/004（run と自動作成）を確定要件化
- ワンショット・broker 埋め込みを明示的にスコープ外化

  実装時に運用感を見て再検討可。
